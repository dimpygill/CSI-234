1. Why databases need indexes

An index is a search structure that helps SQL Server locate rows without examining every row in a table. Think of looking for an author in a bookstore catalog: a catalog organized by author lets you narrow the search quickly. The catalog takes space and must be updated when books change.

Suppose ORDERS contains one million rows. A query for one customer might otherwise read many pages to find that customer's orders. A suitable index can narrow the search to a smaller key range. The actual improvement depends on how many rows match, which columns are needed, and the plan SQL Server chooses.

  • Filtering: find one customer, category, or date range.
  • Joining: locate matching order details or customer rows.
  • Ordering: an appropriate key order may avoid a separate Sort operation.
  • Grouping: ordered input can sometimes support an efficient aggregation plan.

Indexes do not change the query's intended answer. They change the available ways to retrieve it. They are maintained automatically after INSERT, UPDATE, and DELETE operations, so faster reads can come with extra storage and write work.

2. Three terms that describe different properties

TermMeaningExample
ClusteredThe leaf level contains the table rows, organized by the clustering key. A rowstore table has at most one.ORDERS clustered on OrderID
NonclusteredA separate structure with search keys and row locators; it can carry additional columns.An index on BOOKS(Category)
CompositeAn index key containing two or more columns; it can be clustered or nonclustered.ORDERS(CustomerID, OrderDate)

Composite is not a third storage type. “Nonclustered composite index” means a separate index with multiple key columns. “Clustered composite index” means the table's clustered organization uses multiple key columns.

4. Clustered index: the table at the leaf level

The setup explicitly creates a clustered primary-key index on ORDERS(OrderID). The clustering key is OrderID; leaf pages contain the full order rows. Upper levels help navigate to leaf pages. This is a logical key organization, not a promise that every page sits consecutively on disk.

Illustrative leaf keyCustomerIDOrderDateStoreLocation
100112026-09-01Vancouver
100222026-09-03Seattle
100312026-09-10Vancouver
-- The clustered primary key already exists; query it.
SELECT OrderID, CustomerID, OrderDate, StoreLocation, Salesperson
FROM dbo.ORDERS
WHERE OrderID = 1003;

-- A range on the clustering key can also be useful.
SELECT OrderID, CustomerID, OrderDate
FROM dbo.ORDERS
WHERE OrderID BETWEEN 1002 AND 1004
ORDER BY OrderID;

The first query returns order 1003: customer 1, September 10, Vancouver, Priya. The second returns orders 1002, 1003, and 1004. SQL Server may choose a clustered index seek, although a scan can still be reasonable for a small table.

Always use ORDER BY when output order matters. A clustered index does not guarantee SELECT result order.

Common clustered-key considerations are a narrow key, stable values, and an insertion pattern suitable for the workload. A wide clustering key increases the row-locator burden in nonclustered indexes. Sequential keys can reduce some random-insertion page splits but can introduce last-page contention under heavy concurrent inserts.

5. Primary key and clustered index are separate ideas

A primary key is a constraint that enforces unique, non-NULL identification. Clustered describes storage organization. SQL Server commonly creates a clustered index for a primary key when no clustered index already exists and NONCLUSTERED is not specified. The choice can be explicit.

-- Separate demonstration table, not a replacement for ORDERS.
CREATE TABLE dbo.IndexLayoutDemo (
    DemoID INT NOT NULL,
    CreatedDate DATE NOT NULL,
    Note VARCHAR(80) NULL,
    CONSTRAINT PK_IndexLayoutDemo PRIMARY KEY NONCLUSTERED (DemoID)
);
-- Before this statement, the table is a heap with a nonclustered PK.
CREATE CLUSTERED INDEX CX_IndexLayoutDemo_CreatedDate_DemoID
ON dbo.IndexLayoutDemo (CreatedDate, DemoID);

INSERT dbo.IndexLayoutDemo VALUES
(1,'20261001','First record'), (2,'20261001','Second record');
SELECT DemoID, CreatedDate, Note
FROM dbo.IndexLayoutDemo
ORDER BY CreatedDate, DemoID;

This table has a nonclustered primary key on DemoID and a composite clustered index on (CreatedDate, DemoID). A second clustered index on this table would fail because one already exists. A nonunique clustered index is permitted; SQL Server handles duplicate clustered keys internally. A primary key, however, must be unique.

6. Nonclustered index: another route to the rows

BOOKS is clustered by BookID. Searching Category is a different access pattern. A nonclustered index stores Category keys separately and carries a row locator. On this clustered table, the locator is based on BookID. On a heap, it uses a row identifier (RID).

-- Run once after setup.
CREATE NONCLUSTERED INDEX IX_BOOKS_Category
ON dbo.BOOKS (Category);

SELECT BookID, Title, Price
FROM dbo.BOOKS
WHERE Category = 'Programming'
ORDER BY BookID;

The query returns books 101 and 103. The index can locate the Programming entries. Title and Price are not stored in this simple index, so an index-based plan may retrieve them from the clustered index using Key Lookup operations. The optimizer can instead choose a scan when that is cheaper.

Duplicate Category values are valid in a nonunique index. Creating a regular index does not require categories to be unique.

7. Composite index: why column order matters

A composite key is ordered by its first column, then by its second within equal first-column values. For (CustomerID, OrderDate), orders are grouped by customer and ordered by date inside each customer. This is one index, not two independent indexes.

CREATE NONCLUSTERED INDEX IX_ORDERS_CustomerID_OrderDate
ON dbo.ORDERS (CustomerID, OrderDate);

SELECT OrderID, CustomerID, OrderDate
FROM dbo.ORDERS
WHERE CustomerID = 1
  AND OrderDate >= '20260901'
  AND OrderDate < '20261001'
ORDER BY OrderDate;

PredicateFit for (CustomerID, OrderDate)
CustomerID = 1Can use the leading key to seek.
CustomerID = 1 AND OrderDate >= a dateCan seek into a customer/date range.

CustomerID > 1 AND OrderDate = a dateThe leading range can limit seeking; the date condition may be evaluated as a residual predicate.

A practical starting point is equality keys followed by range or ordering keys. Choose the actual order from important queries and measured plans. “Put the most selective column first” is not a universal rule.

8. Compare the reverse key order

-- A different candidate for searches by date across all customers.
CREATE NONCLUSTERED INDEX IX_ORDERS_OrderDate_CustomerID
ON dbo.ORDERS (OrderDate, CustomerID);

SELECT OrderID, CustomerID, OrderDate
FROM dbo.ORDERS
WHERE OrderDate >= '20261001'
  AND OrderDate < '20261101'
ORDER BY OrderDate, CustomerID;

This returns orders 1005 and 1006. Date-first ordering suits a date range across all customers. Customer-first ordering suits a single customer's history. Both indexes are shown to explain the tradeoff; do not retain both automatically in a real system.

Two single-column indexes are also not equivalent to one composite index. SQL Server may combine indexes in some plans, but that does not provide the same ordered key structure or cost.

9. INCLUDE and covering indexes

A covering index contains the columns needed by a particular query. Coverage is a relationship between an index and a query. Key columns support navigation and key ordering; included columns provide extra values at the leaf level without becoming search keys.

-- Replace the simple Category index with a covering version.
-- Run after section 6; avoid keeping duplicate key definitions.
CREATE NONCLUSTERED INDEX IX_BOOKS_Category
ON dbo.BOOKS (Category)
INCLUDE (Title, Price)
WITH (DROP_EXISTING = ON);

SELECT BookID, Title, Price
FROM dbo.BOOKS
WHERE Category = 'Programming';

The leaf entries now provide Category, Title, Price, and the BookID clustering locator. This query can be answered from the index without fetching Title and Price through Key Lookups. The optimizer still chooses the plan.

INCLUDE (Title, Price) does not organize the index by Title or Price. A Price-only filter cannot treat Price as a seek key merely because it is included. Including every column can create a large, expensive structure; include only useful columns for the target workload.

DefinitionKey property
(Category, Price)Two key columns; ordered by category then price.
(Category) INCLUDE (Price)One key column; Price is available as leaf payload.

10. Indexes for joins and sales queries

-- ORDER_DETAILS already has clustered (OrderID, BookID).
-- Its leading OrderID supports fetching details for one order.
SELECT o.OrderID, b.Title,
       od.Quantity * od.UnitPrice * (1 - od.Discount / 100.0) AS SalesAmount
FROM dbo.ORDERS AS o
JOIN dbo.ORDER_DETAILS AS od ON od.OrderID = o.OrderID
JOIN dbo.BOOKS AS b ON b.BookID = od.BookID
WHERE o.OrderID = 1001
ORDER BY b.BookID;

-- Candidate for finding all purchases of a particular book.
CREATE NONCLUSTERED INDEX IX_ORDER_DETAILS_BookID
ON dbo.ORDER_DETAILS (BookID)
INCLUDE (Quantity, UnitPrice, Discount);

SELECT od.OrderID,
       SUM(od.Quantity * od.UnitPrice * (1 - od.Discount / 100.0)) AS TotalSales
FROM dbo.ORDER_DETAILS AS od
WHERE od.BookID = 101
GROUP BY od.OrderID
ORDER BY od.OrderID;

The first result contains Python Foundations (72.00) and SQL in Practice (50.00). The second contains order 1001 (72.00) and order 1006 (40.00). The new index targets BookID searches; the clustered key starts with OrderID, which targets a different path.

Foreign-key creation does not automatically create an index on the referencing columns. Inspect existing indexes before adding one: ORDER_DETAILS already has an OrderID-leading index, and the customer/date index already starts with ORDERS.CustomerID. Indexes can support joins, but a query reading most rows may reasonably use scans and a hash join.

11. How to measure instead of guessing

  1. Use a larger lab table for a meaningful comparison.
  2. In SSMS, choose Query → Include Actual Execution Plan (Ctrl+M).
  3. Run the baseline query with STATISTICS IO and TIME enabled.
  4. Create the candidate index and run exactly the same query.
  5. Compare logical reads, CPU and elapsed time, operators, and actual versus estimated row counts.
  6. Repeat cautiously: cache state and competing work influence timing. Record your own measurements.

The four-to-eight-row bookstore tables teach syntax and results; they do not demonstrate reliable speed differences. The following separate table contains 100,000 generated rows and begins as a heap.

12. Write predicates that can use indexes

SARGable means a search predicate can support an index search. Avoid unnecessary functions on indexed columns when an equivalent direct comparison exists. It still takes a suitable index and a favorable plan to obtain a seek.

-- Less suitable for seeking by OrderDate:
SELECT OrderID, OrderDate FROM dbo.ORDERS
WHERE YEAR(OrderDate) = 2026 AND MONTH(OrderDate) = 9;

-- Direct date range:
SELECT OrderID, OrderDate FROM dbo.ORDERS
WHERE OrderDate >= '20260901' AND OrderDate < '20261001';

-- A prefix can define a key range on an appropriate Title index:
CREATE NONCLUSTERED INDEX IX_BOOKS_Title ON dbo.BOOKS (Title);
SELECT BookID, Title FROM dbo.BOOKS WHERE Title LIKE 'Python%';

-- A leading wildcard usually prevents a normal Title-key seek:
SELECT BookID, Title FROM dbo.BOOKS WHERE Title LIKE '%Python%';

Both date queries return orders 1001–1004 in this sample, although their displayed order is unspecified. Both Title queries return book 101. Matching results do not imply identical access paths. Also use parameter types compatible with column types; implicit conversions on an indexed column can hinder efficient access.

13. Storage, updates, uniqueness, and maintenance

  • INSERT adds entries to relevant indexes; DELETE removes them.
  • UPDATE may change key placement or leaf payload when indexed or included values change.
  • More indexes increase storage, logging, and maintenance work.
  • Statistics help the optimizer estimate row counts; inaccurate estimates can affect plan choice.
  • Page splits and low page density can affect reads and writes, but maintenance should follow evidence rather than a fixed “rebuild everything” rule.

UNIQUE is another independent property: it enforces uniqueness of the complete index key. A unique composite key allows repetition of individual columns as long as the complete combination is unique. Index creation fails if existing rows violate uniqueness.

-- Optional uniqueness demonstration on the demo table.
CREATE UNIQUE NONCLUSTERED INDEX UX_IndexLayoutDemo_Note
ON dbo.IndexLayoutDemo (Note);
-- This is valid for the current distinct notes. A future duplicate note fails.

-- Inspect indexes, including PK-created indexes.
SELECT OBJECT_NAME(i.object_id) AS TableName,
       i.name AS IndexName, i.type_desc,
       i.is_unique, i.is_primary_key
FROM sys.indexes AS i
WHERE i.object_id IN (
    OBJECT_ID('dbo.BOOKS'), OBJECT_ID('dbo.ORDERS'),
    OBJECT_ID('dbo.ORDER_DETAILS'), OBJECT_ID('dbo.CUSTOMERS'))
ORDER BY TableName, i.index_id;

-- Inspect key order and included columns for ORDERS.
SELECT i.name AS IndexName, c.name AS ColumnName,
       ic.key_ordinal, ic.is_descending_key, ic.is_included_column
FROM sys.indexes AS i
JOIN sys.index_columns AS ic
 ON ic.object_id = i.object_id AND ic.index_id = i.index_id
JOIN sys.columns AS c
 ON c.object_id = ic.object_id AND c.column_id = ic.column_id
WHERE i.object_id = OBJECT_ID('dbo.ORDERS')
ORDER BY i.name, ic.key_ordinal, ic.index_column_id;

The catalog query shows explicitly defined key and included columns; clustering locator columns implicitly carried by a nonclustered index may not appear there. Primary-key indexes are managed through their constraints, so do not treat them like ordinary removable secondary indexes.

14. A practical index-design checklist

  1. Start with a specific frequent or expensive query.
  2. Identify equality conditions, ranges, join columns, requested ordering, and returned columns.
  3. Inspect existing indexes and constraints for overlap.
  4. Choose a candidate key order that matches the query pattern.
  5. Include extra returned columns only when coverage is worth the added size.
  6. Compare the actual plan and logical reads on representative data.
  7. Check the effect on writes and other important queries.
  8. Keep the indexes that earn their cost; remove redundant candidates carefully.
Query patternCandidate
Lookup by OrderIDExisting ORDERS clustered primary key.
One customer's date rangeORDERS(CustomerID, OrderDate).
Date range across customersORDERS(OrderDate, CustomerID), or a narrower OrderDate index according to the query.
Category search returning title and priceBOOKS(Category) INCLUDE (Title, Price).
Details for one orderExisting ORDER_DETAILS(OrderID, BookID) clustered key.
Sales lines for one bookORDER_DETAILS(BookID) INCLUDE (Quantity, UnitPrice, Discount).

15. Practice questions and explained answers

Each answer appears directly beneath its question. Click its heading to collapse it. SQL creation answers are optional extensions and should be run once in the same lab database.

Question 1

Why can an index make a customer lookup faster?

Answer and explanation

It supplies an ordered search path to matching keys, which can reduce pages read. The benefit depends on selectivity, coverage, table size, and the chosen plan.

Question 2

Can one rowstore table have two clustered indexes?

Answer and explanation

No. It has one clustered organization, or it is a heap. It can have multiple nonclustered indexes.

Question 3

Is a composite index always nonclustered?

Answer and explanation

No. Composite describes the number of key columns. ORDER_DETAILS has a composite clustered primary key; the customer/date index is composite and nonclustered.

Question 4

Create an index for finding books by AuthorName.

Answer and explanation

A nonclustered key on AuthorName provides a candidate author-search path. Run this new index once after setup.

CREATE NONCLUSTERED INDEX IX_BOOKS_AuthorName
ON dbo.BOOKS (AuthorName);
SELECT BookID, Title FROM dbo.BOOKS
WHERE AuthorName = 'Anita Rao';

Question 5

What results should the previous author query return?

Answer and explanation

Book 101, Python Foundations, and book 103, Learning C Sharp. Without ORDER BY their display order is not guaranteed.

Question 6

Design an index for one salesperson within one store. Return OrderID and OrderDate.

Answer and explanation

An equality key on store followed by salesperson is suitable for this pattern. OrderDate is payload; OrderID is already the clustering locator.

CREATE NONCLUSTERED INDEX IX_ORDERS_StoreLocation_Salesperson
ON dbo.ORDERS (StoreLocation, Salesperson)
INCLUDE (OrderDate);
SELECT OrderID, OrderDate FROM dbo.ORDERS
WHERE StoreLocation = 'Vancouver' AND Salesperson = 'Priya';

Question 7

Does (CustomerID, OrderDate) efficiently support every date-only search?

Answer and explanation

It is organized by customer first, so a date-only condition usually cannot seek a single contiguous date range. SQL Server might still scan that index. A date-leading index is a more direct candidate.

Question 8

Why are (CustomerID, OrderDate) and (OrderDate, CustomerID) different?

Answer and explanation

They have different leading ranges. One favors a customer history; the other favors searching a date interval across customers.

Question 9

An index has key Category and INCLUDE (Title, Price). Is Price a seek key?

Answer and explanation

No. It is leaf payload. It can cover a query but does not establish Price key order.

Question 10

Create a covering index for searches by author that return Title and Price.

Answer and explanation

Replace the author index from Question 4 rather than adding a duplicate author key. BookID is available through the clustered locator.

CREATE NONCLUSTERED INDEX IX_BOOKS_AuthorName
ON dbo.BOOKS (AuthorName) INCLUDE (Title, Price)
WITH (DROP_EXISTING = ON);

Question 11

What is a Key Lookup, and how can coverage help?

Answer and explanation

A Key Lookup retrieves columns missing from a nonclustered access path from clustered rows. Including necessary output columns can eliminate those lookups for the target query; the resulting index still has storage and write costs.

Question 12

Does creating a foreign key automatically index its referencing columns?

Answer and explanation

No. Inspect the referencing table and add a useful index only if the workload benefits. A suitable existing composite index may already start with the foreign-key column.

Question 13

Rewrite a query that filters WHERE YEAR(OrderDate) = 2026 into a direct range.

Answer and explanation

Use a half-open range. This also remains correct if the column later becomes a date/time type.

SELECT OrderID, OrderDate FROM dbo.ORDERS
WHERE OrderDate >= '20260101' AND OrderDate < '20270101';

Question 14

A query uses an index scan. Is that automatically a bad plan?

Answer and explanation

No. A scan can be cheaper for a small table, a broad result, or a narrow covering index. Evaluate rows read, logical reads, estimates, and actual workload costs.

Question 15

Does an index guarantee that SELECT results appear in index-key order?

Answer and explanation

No. Use ORDER BY explicitly. A plan can choose a different path or use parallel operations.

Question 16

What does the ORDER_DETAILS primary key (OrderID, BookID) enforce?

Answer and explanation

The complete pair must be unique and both columns are non-NULL. A book can appear in multiple orders. An order can contain multiple different books.

Question 17

What happens if a second index is created with the same name on the same table?

Answer and explanation

Creation fails unless an appropriate replacement option is used. Run creation examples once; the Category and AuthorName covering examples use DROP_EXISTING to replace their previous definitions.

Question 18

Why not index every column?

Answer and explanation

That increases storage and the work required by writes. Many indexes may overlap or offer little benefit. Design around measured query patterns.

Question 19

How do you verify that the performance-lab index helps?

Answer and explanation

Run the same query before and after, enable the actual execution plan, and compare STATISTICS IO logical reads and timing. Both results must return 100 rows. Do not invent a speedup percentage from the tiny sample.

Question 20

What index would you start with for a query WHERE Category = ... AND Price >= ... ORDER BY Price?

Answer and explanation

Consider the composite key (Category, Price): equality on Category followed by a price range can fit the requested order. Include Title if it is returned. Validate its value against the existing Category index before keeping both.

CREATE NONCLUSTERED INDEX IX_BOOKS_Category_Price
ON dbo.BOOKS (Category, Price) INCLUDE (Title);
SELECT BookID, Title, Price FROM dbo.BOOKS
WHERE Category = 'Database' AND Price >= 50.00
ORDER BY Price;

Question 21

Can ROLLUP, CUBE, or RANK queries benefit from indexes?

Answer and explanation

Sometimes. Indexes can reduce input through filters, cover needed columns, or provide useful ordering. Full-table aggregation may still need a scan. An index does not compute the final subtotal or rank for every query automatically.

Question 22

DROP INDEX removes the index, not the books. Do not drop the BOOKS primary-key constraint for this task.

DROP INDEX IX_BOOKS_AuthorName ON dbo.BOOKS;
