SQL Server Triggers — Part A: AFTER Triggers

Learning goals: Explain triggers, distinguish DML/DDL/LOGON triggers, create AFTER INSERT/UPDATE/DELETE triggers, and interpret the inserted and deleted pseudo-tables. You will also enforce business rules with ROLLBACK, write multi-row-safe triggers, use UPDATE(), and manage (view, disable, drop) triggers.

1. What is a trigger?

A trigger is a stored database program automatically invoked by a specified event. Unlike a stored procedure, you do not normally call a DML trigger explicitly. Triggers can support auditing and enforcing business rules, but they also add hidden work to data changes.

2. SQL Server trigger categories

CategoryTypical eventsIn this course?
DMLINSERT, UPDATE, DELETEYes
DDLCREATE, ALTER, DROPNo
LOGONSession logon eventNo

DML triggers can be AFTER or INSTEAD OF. This week covers AFTER; next week covers INSTEAD OF.

2.1 DDL triggers (overview only)

A DDL trigger fires when the structure of the database changes — for example when someone runs CREATE TABLE, ALTER TABLE, or DROP TABLE. It is attached to the whole database (or server), not to a single table. Organizations use DDL triggers to record schema changes or to stop someone from accidentally dropping important tables.

2.2 LOGON triggers (overview only)

A LOGON trigger fires when a user connects to SQL Server, after the login and password are accepted but before the session starts. It can refuse the connection — for example, to limit how many sessions one login may open, or to block logins outside working hours. Administrators use them for security and auditing.

Trigger typeFires when…Attached to
DMLData changes (INSERT, UPDATE, DELETE)A table
DDLStructure changes (CREATE, ALTER, DROP)A database or the server
LOGONA user connectsThe server

DDL and LOGON triggers are not practiced in this course. The rest of this tutorial focuses on DML AFTER triggers.

3. AFTER triggers

An AFTER trigger executes after the triggering statement has performed its data changes and passed applicable constraint checks, but before its transaction commits. An error can roll back the transaction. SQL Server DML triggers fire once per statement, not once per row.

3.1 Syntax

CREATE OR ALTER TRIGGER schema.trigger_name
ON schema.table_name
AFTER { INSERT | UPDATE | DELETE } [ , ...n ]   -- FOR is a synonym for AFTER
AS
BEGIN
 SET NOCOUNT ON;          -- stop extra "(n rows affected)" messages
 -- set-based logic that reads inserted and/or deleted
END;
GO

One trigger can respond to several events, for example AFTER INSERT, UPDATE. CREATE OR ALTER (SQL Server 2016 SP1 and later) creates the trigger, or replaces it if it already exists.

3.2 What happens, step by step

  1. The application runs an INSERT, UPDATE, or DELETE statement.
  2. SQL Server checks constraints (PRIMARY KEY, UNIQUE, FOREIGN KEY, CHECK, NOT NULL). If a constraint fails, the statement fails and the AFTER trigger never runs.
  3. The rows are changed in the table, and the affected rows are copied into inserted and/or deleted.
  4. Every AFTER trigger defined for that event runs (once each).
  5. If any trigger raises an error or runs ROLLBACK TRANSACTION, the statement and everything else in the transaction is undone. Otherwise the transaction commits (in autocommit mode) or stays open until your COMMIT.

3.3 Key facts to remember

FactWhy it matters
FOR = AFTEROlder scripts use FOR INSERT; it behaves exactly like AFTER INSERT.
AFTER triggers are allowed on tables onlyViews can only have INSTEAD OF triggers (next week).
A table can have many AFTER triggers for the same eventEach one runs; do not rely on the order in which they run.
The trigger fires even when 0 rows are affectedAlways write logic that works when inserted/deleted are empty.
TRUNCATE TABLE does not fire DELETE triggersAn audit trigger will not capture a truncate.
BULK INSERT/bcp skip triggers unless FIRE_TRIGGERS is specifiedBulk loads can bypass your rules.

3.4 Useful functions inside an AFTER trigger

FunctionReturns
UPDATE(ColumnName)In an UPDATE trigger: TRUE if the column appears in the SET list (even if the value did not actually change). In an INSERT trigger it is TRUE for every column, because every column receives a value (explicit, default, or NULL).

@@ROWCOUNTRows affected by the triggering statement — but only if read as the very first statement (even SET NOCOUNT ON resets it). Prefer EXISTS (SELECT 1 FROM inserted).

3.5 Trigger or constraint?

Use the simplest tool that works. A rule about one row of one table (e.g., Credits ≥ 0) belongs in a CHECK constraint — it is faster, visible, and cannot be disabled by accident as easily. Use an AFTER trigger when you need to record history, compare old and new values, change another table, or enforce a rule that spans tables or rows.

4. Magic tables (logical pseudo-tables)

Inside a DML trigger, inserted and deleted expose sets of affected rows. They are not permanent tables.

Eventinserteddeleted
INSERTNew rowsEmpty
UPDATENew versionsOld versions
DELETEEmptyOld/deleted rows
  • Both have the same columns as the trigger's table.
  • They are read-only: you can SELECT and JOIN them, but not INSERT, UPDATE, or DELETE them.
  • They exist only while the trigger runs and are visible only inside that trigger.
  • For an UPDATE, match old and new rows by joining on the primary key: inserted i JOIN deleted d ON i.PK = d.PK.
  • You can tell which event fired a multi-event trigger: rows in both = UPDATE; only inserted = INSERT; only deleted = DELETE; neither = zero rows affected.

6. AFTER INSERT: record new students

Flow: INSERT statement → new row in Students → AFTER trigger reads inserted → audit record.

CREATE OR ALTER TRIGGER dbo.trg_Students_AfterInsert
ON dbo.Students AFTER INSERT AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.StudentAudit(StudentID,ActionType,OldCredits,NewCredits)
 SELECT StudentID,'INSERT',NULL,Credits FROM inserted;
END;
GO
INSERT INTO dbo.Students(StudentID,StudentName,Credits)
VALUES (1,N'Ana',20),(2,N'Ben',35);
SELECT * FROM dbo.Students;
SELECT StudentID,ActionType,OldCredits,NewCredits FROM dbo.StudentAudit ORDER BY AuditID;

Expected: two Students rows and two INSERT audit rows; OldCredits is NULL and NewCredits is 20 or 35.

7. AFTER UPDATE: compare old and new values

Flow: UPDATE → deleted has previous Credits → inserted has new Credits → trigger logs changed values.

CREATE OR ALTER TRIGGER dbo.trg_Students_AfterUpdate
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.StudentAudit(StudentID,ActionType,OldCredits,NewCredits)
 SELECT i.StudentID,'UPDATE',d.Credits,i.Credits
 FROM inserted AS i JOIN deleted AS d ON i.StudentID=d.StudentID
 WHERE i.Credits<>d.Credits;
END;
GO
UPDATE dbo.Students SET Credits=Credits+5 WHERE StudentID=1;
SELECT StudentID,ActionType,OldCredits,NewCredits FROM dbo.StudentAudit ORDER BY AuditID;

Expected: an UPDATE audit entry for student 1, OldCredits 20, NewCredits 25. The join handles multiple updated students, too.

8. AFTER DELETE: retain deleted values in the audit

CREATE OR ALTER TRIGGER dbo.trg_Students_AfterDelete
ON dbo.Students AFTER DELETE AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.StudentAudit(StudentID,ActionType,OldCredits,NewCredits)
 SELECT StudentID,'DELETE',Credits,NULL FROM deleted;
END;
GO
DELETE FROM dbo.Students WHERE StudentID=2;
SELECT * FROM dbo.Students;
SELECT StudentID,ActionType,OldCredits,NewCredits FROM dbo.StudentAudit ORDER BY AuditID;

Expected: student 2 is absent from Students; a DELETE audit entry shows OldCredits 35 and NewCredits NULL.

9. Multi-row thinking: the #1 trigger mistake

Because a trigger fires once per statement, inserted and deleted may hold 0, 1, or many rows. Code that copies a value into a variable silently handles only one of them.

-- DON'T DO THIS (shown for discussion only — do not create it)
CREATE OR ALTER TRIGGER dbo.trg_Bad_Insert
ON dbo.Students AFTER INSERT AS
BEGIN
 DECLARE @id INT, @credits INT;
 SELECT @id = StudentID, @credits = Credits FROM inserted;   -- keeps only ONE row
 INSERT INTO dbo.StudentAudit(StudentID,ActionType,OldCredits,NewCredits)
 VALUES (@id,'INSERT',NULL,@credits);
END;
StatementBad trigger resultSet-based trigger (Section 6) result
INSERT 1 row1 audit row ✔1 audit row ✔
INSERT 3 rows1 audit row ✘ (2 lost)3 audit rows ✔

Rule: write trigger logic as INSERT … SELECT … FROM inserted/deleted or IF EXISTS (…). Avoid variables that hold one row's value.

11. More AFTER INSERT examples

Example 11.1 — Log a message for each new student

CREATE OR ALTER TRIGGER dbo.trg_Students_InsertMessage
ON dbo.Students AFTER INSERT AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.ActivityLog(Message)
 SELECT N'New student added: ' + StudentName FROM inserted;
END;
GO
INSERT INTO dbo.Students(StudentID,StudentName,Credits)
VALUES (3,N'Chen',40),(4,N'Dia',10);
SELECT Message FROM dbo.ActivityLog ORDER BY LogID;
DROP TRIGGER dbo.trg_Students_InsertMessage;

Expected: two messages — “New student added: Chen” and “New student added: Dia”. One INSERT statement, one trigger run, two rows handled.

Example 11.2 — Reject a new student with too many credits

If the trigger finds bad data, ROLLBACK TRANSACTION cancels the INSERT and THROW sends an error message to the user.

CREATE OR ALTER TRIGGER dbo.trg_Students_InsertCreditLimit
ON dbo.Students AFTER INSERT AS
BEGIN
 SET NOCOUNT ON;
 IF EXISTS (SELECT 1 FROM inserted WHERE Credits > 200)
 BEGIN
  ROLLBACK TRANSACTION;
  THROW 50001, N'A new student cannot have more than 200 credits.', 1;
 END
END;
GO
INSERT INTO dbo.Students(StudentID,StudentName,Credits) VALUES (5,N'Eli',250);  -- fails
GO
SELECT * FROM dbo.Students WHERE StudentID = 5;   -- no rows
DROP TRIGGER dbo.trg_Students_InsertCreditLimit;

Expected: Msg 50001, and Eli is not in the table. The INSERT audit row from Section 6 is also undone — a rollback cancels everything in the transaction. (For a simple one-column rule like this, a CHECK constraint is usually the better tool; the trigger version shows the ROLLBACK pattern.)

12. More AFTER UPDATE examples

Example 12.1 — Log name changes

CREATE OR ALTER TRIGGER dbo.trg_Students_NameChange
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.ActivityLog(Message)
 SELECT N'Name changed from ' + d.StudentName + N' to ' + i.StudentName
 FROM inserted AS i JOIN deleted AS d ON i.StudentID = d.StudentID
 WHERE i.StudentName <> d.StudentName;
END;
GO
UPDATE dbo.Students SET StudentName = N'Ana Lopez' WHERE StudentID = 1;
SELECT Message FROM dbo.ActivityLog ORDER BY LogID;
DROP TRIGGER dbo.trg_Students_NameChange;

Expected: a new message “Name changed from Ana to Ana Lopez”. deleted supplied the old name, inserted the new one.

Example 12.2 — Do not allow Credits to go down

CREATE OR ALTER TRIGGER dbo.trg_Students_NoCreditDecrease
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 IF EXISTS (SELECT 1
            FROM inserted AS i JOIN deleted AS d ON i.StudentID = d.StudentID
            WHERE i.Credits < d.Credits)
 BEGIN
  ROLLBACK TRANSACTION;
  THROW 50002, N'Credits cannot be decreased.', 1;
 END
END;
GO
UPDATE dbo.Students SET Credits = Credits - 5 WHERE StudentID = 1;  -- fails
GO
SELECT StudentID, Credits FROM dbo.Students WHERE StudentID = 1;  -- still 25
DROP TRIGGER dbo.trg_Students_NoCreditDecrease;

Expected: Msg 50002; Ana still has 25 credits. This rule compares old and new values, which a CHECK constraint cannot do — a good reason to use a trigger.

Example 12.3 — Log when a student is deactivated

CREATE OR ALTER TRIGGER dbo.trg_Students_Deactivated
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.ActivityLog(Message)
 SELECT N'Student deactivated: ' + i.StudentName
 FROM inserted AS i JOIN deleted AS d ON i.StudentID = d.StudentID
 WHERE d.IsActive = 1 AND i.IsActive = 0;
END;
GO
UPDATE dbo.Students SET IsActive = 0 WHERE StudentID = 4;
SELECT Message FROM dbo.ActivityLog ORDER BY LogID;
DROP TRIGGER dbo.trg_Students_Deactivated;

Expected: “Student deactivated: Dia”. The WHERE clause checks the old value (d.IsActive = 1) and the new value (i.IsActive = 0).

15. Best practices and common mistakes

DoAvoid
Start with SET NOCOUNT ON.Extra “rows affected” messages that confuse applications.
Write set-based logic over inserted/deleted.Variables or loops that process one row.
Join old and new rows on the primary key.Allowing primary-key updates that break that join.

16. Check your understanding

1. Why does an AFTER trigger not need an explicit EXEC call?
2. For UPDATE, which pseudo-table holds the previous values?
3. What happens if one UPDATE statement affects 10 rows?
4. Why is an audit table useful?
Show answers

1. The trigger is bound to a table and an event. SQL Server runs it automatically whenever that INSERT, UPDATE, or DELETE occurs on that table.
2. deleted holds the old (before) values; inserted holds the new (after) values.
3. The trigger fires once. Both inserted and deleted contain 10 rows, so the trigger must use set-based code to handle all of them.
4. It keeps a permanent history of who changed what and when — supporting accountability, troubleshooting, recovery of old values, and compliance requirements.

Choose the best answer, then open the answer to check yourself.

Q1. When does an AFTER UPDATE trigger run?
A. Before the rows are changed
B. Instead of the UPDATE
C. After the rows are changed and constraints pass, before the transaction commits
D. After the transaction commits
Show answer

C. The trigger runs inside the same transaction, which is why it can still roll the change back.

Q2. CREATE TRIGGER … FOR INSERT is the same as:
A. INSTEAD OF INSERT
B. AFTER INSERT
C. BEFORE INSERT
D. A DDL trigger
Show answer

B. FOR is a synonym for AFTER. SQL Server has no BEFORE triggers.

Q3. In an AFTER INSERT trigger, the inserted table contains:
A. The new rows
B. All rows in the table
C. The old rows
D. Nothing
Show answer

A. Only the rows added by the INSERT statement. deleted is empty.

Q4. During a DELETE trigger, the inserted table is:
A. Empty
B. The deleted rows
C. All rows still in the table
D. Not accessible — causes an error
Show answer

A. A DELETE creates no new rows. The removed rows are in deleted.

Q5. In an AFTER UPDATE trigger, where are the old values?
A. inserted
B. deleted
C. StudentAudit
D. They are lost
Show answer

B. deleted = before, inserted = after.

Q6. An UPDATE changes 50 rows. How many times does the AFTER UPDATE trigger fire?
A. 50
B. 1
C. 51
D. 0
Show answer

B. Once per statement. inserted and deleted each contain 50 rows.

Q7. Can you create an AFTER trigger on a view?
A. Yes
B. Only AFTER DELETE
C. No — views support only INSTEAD OF triggers
D. Only if the view has one base table
Show answer

C. AFTER triggers are for tables only.

A. Fire the AFTER DELETE trigger once
B. Fire it once per row
C. Not fire DELETE triggers
D. Fire the INSERT trigger
Show answer

C. TRUNCATE does not fire DELETE triggers, so an audit trigger will not record it.

Q9. An INSERT violates a CHECK constraint. What happens to the AFTER INSERT trigger?
A. It runs and can fix the data
B. It runs, then the statement fails
C. It never runs, because the statement fails first
D. It runs twice
Show answer

C. Constraints are checked before AFTER triggers run.

Q10. UPDATE dbo.Students SET Credits = 0 WHERE StudentID = 999 matches no rows. The AFTER UPDATE trigger:
A. Does not fire
B. Fires with empty inserted and deleted
C. Fires with all rows
D. Raises an error
Show answer

B. The trigger fires for the statement regardless of row count.

Q11. ROLLBACK TRANSACTION inside an AFTER trigger undoes:
A. Only the trigger's own inserts
B. Only the last row
C. The triggering statement and all other work in the same transaction
D. Nothing — triggers cannot roll back
Show answer

C. In Example 11.2, the audit row written by the Section 6 trigger was undone too.

Q12. Why put SET NOCOUNT ON at the start of a trigger?
A. To make the trigger fire once
B. To stop extra “rows affected” messages being returned to the application
C. To disable the trigger
D. To hide errors

B. Some applications misread those extra row counts as the result of their own statement.

Q13. Which code is multi-row safe?
A. SELECT @id = StudentID FROM inserted

B. A and D keep one row; C fails with “Subquery returned more than 1 value” when several rows are affected.

18. Practice problems with detailed solutions

Try each problem before opening the solution. Each solution ends by dropping the trigger so problems stay independent. Run them in order — some tests use students added in earlier problems.

Problem 1 — AFTER INSERT: reject very short names. Reject any new student whose name is shorter than 2 characters.
Show solution
CREATE OR ALTER TRIGGER dbo.trg_Students_NameLength
ON dbo.Students AFTER INSERT AS
BEGIN
 SET NOCOUNT ON;
 IF EXISTS (SELECT 1 FROM inserted WHERE LEN(StudentName) < 2)
 BEGIN
  ROLLBACK TRANSACTION;
  THROW 50010, N'Student name must have at least 2 characters.', 1;
 END
END;
GO
INSERT INTO dbo.Students(StudentID,StudentName,Credits) VALUES (10,N'A',5);    -- fails
GO
INSERT INTO dbo.Students(StudentID,StudentName,Credits) VALUES (10,N'Ali',5);  -- works
DROP TRIGGER dbo.trg_Students_NameLength;

Explanation: the new rows are in inserted. EXISTS checks whether any of them breaks the rule; if so, the whole INSERT is cancelled.

Problem 2 — AFTER INSERT: log the starting credits. For each new student, write “New student <name> with <credits> credits” to ActivityLog.
Show solution
CREATE OR ALTER TRIGGER dbo.trg_Students_LogCredits
ON dbo.Students AFTER INSERT AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.ActivityLog(Message)
 SELECT CONCAT(N'New student ', StudentName, N' with ', Credits, N' credits')
 FROM inserted;
END;
GO
INSERT INTO dbo.Students(StudentID,StudentName,Credits) VALUES (11,N'Bo',12);
SELECT Message FROM dbo.ActivityLog ORDER BY LogID;
DROP TRIGGER dbo.trg_Students_LogCredits;

Explanation: CONCAT joins text and numbers without needing CAST. Expected message: “New student Bo with 12 credits”.

Problem 3 — AFTER UPDATE: log credit changes as a sentence. Write “Credits for <name> changed from <old> to <new>” whenever Credits changes.
Show solution
CREATE OR ALTER TRIGGER dbo.trg_Students_LogCreditChange
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.ActivityLog(Message)
 SELECT CONCAT(N'Credits for ', i.StudentName, N' changed from ', d.Credits, N' to ', i.Credits)
 FROM inserted AS i JOIN deleted AS d ON i.StudentID = d.StudentID
 WHERE i.Credits <> d.Credits;
END;
GO

SELECT Message FROM dbo.ActivityLog ORDER BY LogID;
DROP TRIGGER dbo.trg_Students_LogCreditChange;

Explanation: old Credits come from deleted, new Credits from inserted, matched on StudentID. Expected: “Credits for Bo changed from 12 to 17”.

Problem 4 — AFTER UPDATE: maximum credits. Reject any update that sets Credits above 200.
Show solution
CREATE OR ALTER TRIGGER dbo.trg_Students_UpdateCreditLimit
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 IF EXISTS (SELECT 1 FROM inserted WHERE Credits > 200)
 BEGIN

 END
END;

Problem 5 — AFTER UPDATE: protect the primary key. Prevent anyone from changing StudentID.
Show solution
CREATE OR ALTER TRIGGER dbo.trg_Students_NoKeyChange
ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 IF UPDATE(StudentID)
 BEGIN
  ROLLBACK TRANSACTION;
  THROW 50012, N'StudentID cannot be changed.', 1;
 END
END;
GO
UPDATE dbo.Students SET StudentID = 99 WHERE StudentID = 11;   -- fails
GO
DROP TRIGGER dbo.trg_Students_NoKeyChange;

Explanation: UPDATE(StudentID) is TRUE when the column appears in the SET list. Protecting the key matters because update triggers join inserted to deleted on StudentID — if the key changes, old and new rows no longer match.

Problem 6 — AFTER DELETE: record who deleted a student. Write “Student <name> deleted by <login>” to ActivityLog.

Problem 7 — AFTER DELETE: protect high-credit students. Block deleting any student with more than 100 credits.

Problem 8 — AFTER DELETE: one student at a time. Allow a DELETE statement to remove at most one student.
Show solution
CREATE OR ALTER TRIGGER dbo.trg_Students_OneAtATime
ON dbo.Students AFTER DELETE AS
BEGIN
 SET NOCOUNT ON;
 IF (SELECT COUNT(*) FROM deleted) > 1
 BEGIN
  ROLLBACK TRANSACTION;
  THROW 50014, N'Delete one student at a time.', 1;
 END
END;
GO
DELETE FROM dbo.Students WHERE StudentID IN (11,12);   -- 2 rows: fails
GO
DROP TRIGGER dbo.trg_Students_OneAtATime;

Explanation: because the trigger fires once per statement, COUNT(*) on deleted tells you how many rows the statement removed. This protects against a DELETE with a missing or wrong WHERE clause.

Problem 9 — Debug a broken trigger. List the problems in this trigger and rewrite it correctly.
CREATE TRIGGER dbo.trg_Bad ON dbo.Students AFTER UPDATE AS
BEGIN
 DECLARE @id INT, @old INT, @new INT;
 SELECT @id = StudentID, @new = Credits FROM inserted;
 SELECT @old = Credits FROM deleted;
 INSERT INTO dbo.StudentAudit(StudentID,ActionType,OldCredits,NewCredits)
 VALUES (@id,'UPDATE',@old,@new);
END;
Show solution

Problems:

  1. Handles only one row: with 10 updated rows, only one audit row is written.
  2. Old and new values may not match: @new and @old come from two separate SELECTs with no join, so they may belong to different students.
  3. Fails when no rows match: @id is NULL, and inserting NULL into the NOT NULL StudentID column raises an error that cancels the user's UPDATE.
  4. Logs non-changes: an update to StudentName still writes a Credits “change”.
  5. No SET NOCOUNT ON.
CREATE OR ALTER TRIGGER dbo.trg_Bad ON dbo.Students AFTER UPDATE AS
BEGIN
 SET NOCOUNT ON;
 INSERT INTO dbo.StudentAudit(StudentID,ActionType,OldCredits,NewCredits)
 SELECT i.StudentID,'UPDATE',d.Credits,i.Credits
 FROM inserted AS i JOIN deleted AS d ON i.StudentID = d.StudentID
 WHERE i.Credits <> d.Credits;
END;
GO
DROP TRIGGER dbo.trg_Bad;   -- it duplicates Section 7, so remove it

Explanation: the corrected version is the pattern from Section 7: one set-based INSERT…SELECT, a join on the key, and a filter for real changes.
